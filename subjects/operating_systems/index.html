Module 1

OS Fundamentals

Under the hood basics: core components, system execution modes, hardware abstractions, and system call lifecycles.

Core Roles & Components

Explain the role of an OS.

An Operating System (OS) is system software that acts as an intermediary between user applications and physical hardware. Its primary roles include:

  • Resource Allocator: Fairly and efficiently allocates CPU time, memory space, I/O devices, and file storage among competing processes.
  • Control Program: Directs execution of user code, prevents errors, controls access, and prevents improper use of hardware.
  • Hardware Abstraction Layer (HAL): Hides complex, vendor-specific hardware details behind simple, standardized software APIs.

Kernel

The core program of the OS that runs at all times at the lowest level. It has direct, unrestricted access to physical hardware (executes in Kernel Mode) and is responsible for process, memory, filesystem, and device management.

Shell

A user-space command-line interpreter or graphical interface that translates human commands into system calls. It is not part of the kernel; it acts as a user application running in User Mode.

System Modes & Hardware Access

Difference between User Mode and Kernel Mode.

Modern CPUs enforce memory and hardware protection via physical execution modes:

  • User Mode (Mode bit = 1): Restricted mode. The CPU cannot execute privileged instructions (such as disabling interrupts, modifying page tables, or writing directly to hardware ports). Access to memory is bounded to the process's allocated range.
  • Kernel Mode (Mode bit = 0): Unrestricted mode. The CPU can execute any machine instruction and access any physical address in the system. The core OS kernel executes here.

Why can't applications directly access hardware?

If user applications had direct hardware access:

  • Security Violation: An application could read sensitive data directly from disk blocks belonging to other users.
  • System Instability: A bug in one application (e.g., writing to memory-mapped control registers) could corrupt physical memory or crash the entire computer.
  • Complexity: Every developer would need to write low-level code to communicate with specific disk controller chips, network cards, and screen monitors.
System Calls & Interrupts

What is a system call?

A programmatic interface that allows a user-mode application to request services from the kernel (e.g., reading a file, spawning a process, sending packets). It transitions the CPU from User Mode to Kernel Mode via a controlled software interrupt/trap.

fork() vs. exec()

fork(): Spawns a new child process by duplicating the calling parent process's memory space, descriptors, and execution state. Both execute the next instruction.

exec(): Replaces the entire address space and code image of the current process with a new executable program. It does not create a new process; it overwrites the current one.

Interrupt vs. Exception

Interrupt: An asynchronous event generated by external hardware (e.g., timer clock tick, disk write complete, key press) indicating it needs CPU attention.

Exception (Trap): A synchronous event generated by the CPU itself during execution of an instruction due to an error (e.g., divide-by-zero, page fault) or a programmatic request (system call trap).

What is Context Switching? Why is it expensive?

The mechanism of saving the CPU execution state (Program Counter, registers, stack pointer, MMU page tables) of a running process or thread, and loading the saved state of another to resume its execution.

Why it is expensive:

  • Direct Cost: Time spent executing OS scheduler code, saving registers, and updating process state tables.
  • Indirect Cost: Flushing the Translation Lookaside Buffer (TLB) and invalidating L1/L2/L3 caches. When the new process runs, it suffers major cache misses, leading to slow instruction execution until caches are warmed up again.

Module 2

Processes & Threads

Process lifecycle, resources allocation, lightweight executing structures, and thread pool design.

Process Architecture & States

What is a process? What is stored in the PCB?

A Process is an active program instance in execution, isolated by memory boundaries. The OS tracks and manages each process using a kernel data structure called the Process Control Block (PCB), which stores:

  • Process ID (PID) & Process State: Unique identifier and current execution state (New, Ready, Running, Waiting, Terminated).
  • Program Counter (PC): Address of the next CPU instruction to execute for this process.
  • Registers: Saved CPU register values when the process is context-switched out.
  • Memory Management Info: Page tables, segment tables, and base/limit registers representing the virtual address space.
  • File Descriptor Table: Pointers to open files, network sockets, and I/O descriptors.

Program vs. Process

A Program is a passive entity: a compiled binary file containing machine code instructions stored on disk. A Process is an active entity: it represents the active execution of those instructions, possessing resources like virtual memory, registers, stack, and heap allocated by the kernel.

Why are processes isolated?

Processes have completely isolated virtual address spaces. If Process A has a bug (e.g., null pointer dereference or array index write out of bounds), it triggers a segmentation fault. The OS terminates Process A, but Process B continues running completely unaffected. Memory isolation guarantees safety and security.

Process & Thread Lifecycles

Zombie Process

A child process that has completed execution (called `exit()`) but its parent has not yet read its exit status (via `wait()`). It holds an entry in the system process table, though it releases all other memory.

Orphan Process

A process whose parent has terminated while the child is still executing. The child is immediately adopted by the root system process (`init` or PID 1) which cleans up its exit state on termination.

Daemon Process

A background service process that runs continuously, detached from any user session or terminal. It handles system service tasks (e.g., `crond`, `syslogd`, web server listening loops).

Why is creating a process expensive?

Creating a process requires allocating a new PID, setting up a fresh PCB, building new page tables, copying file descriptors, and copying the parent's memory layout (often optimized via **Copy-on-Write**, but still incurs overhead). In contrast, threads simply run inside the existing process environment.

Threads: The Lightweight Alternative

What is a thread? Why is it lightweight?

A Thread is the basic, smallest unit of CPU execution scheduled by the OS. It is "lightweight" because it runs inside its parent process's memory context, avoiding the need to allocate separate virtual memory page tables or address space descriptors.

Shared Resources

  • Code Segment (instructions)
  • Data Segment (global variables)
  • Heap memory (objects, dynamically allocated variables)
  • System resources (open files, sockets)

Private Resources

  • Thread ID (TID)
  • Program Counter (PC)
  • CPU registers
  • Stack (local variables, function call frames)
  • Thread Local Storage (TLS)

Can one thread crash another?

Yes. Because all threads of a process share the same virtual address space, if one thread executes a invalid memory operation (e.g., null pointer dereference, writing outside allocated boundaries), it triggers a segmentation fault at the process level. The OS sends a `SIGSEGV` signal to the parent process, causing the immediate termination of the entire process and all of its executing threads.

Amazon SDE-1 Follow-up Scenario
Question: Suppose your backend server needs to handle 10,000 concurrent client requests. Would you create 10,000 threads? Why or why not? What are the alternatives?

Why 10,000 threads will crash your server:

  1. Memory Exhaustion (Out Of Memory): Each thread requires its own private stack segment. By default on Linux, stack size is 8MB (can be tuned down to 512KB-2MB). At 1MB per thread, 10,000 threads consume 10 GB of RAM just for stack frames, completely starving the application heap.
  2. Context Switching Storm: If 10,000 threads compete for CPU cycles on an 8-core CPU, the CPU spends almost all its time swapping register states, page base pointers, and flushing caches (CPU thrashing). The CPU spends more time on context switching than running actual business logic.
  3. Thread Creation Overhead: Initiating, scheduling, and tearing down 10,000 OS-level kernel threads wastes massive system cycles.

The Production-Grade Alternatives:

  • Thread Pool (Bounded Workers): Maintain a fixed pool of worker threads (e.g., `num_cores * 2`). Incoming requests are placed in a thread-safe task queue. Worker threads poll the queue, process requests, and return to the pool for reuse. This bounds resource usage.
  • Non-blocking Asynchronous I/O (Event Loop / Reactor Pattern): Used in Node.js, Nginx, Netty. A single thread (or one thread per core) multiplexes thousands of active connections using OS event notifications (such as `epoll` on Linux or `kqueue` on macOS). Instead of blocking a thread while waiting on disk/network I/O, the thread registers a callback and instantly moves to the next request. When I/O finishes, the OS raises an event and the thread executes the callback.

CPU Scheduling

CPU allocation algorithms, Gantt chart scheduling evaluations, and queue strategies.

1. Scheduling Terms & Definitions
• Preemption: The OS can interrupt a running process to allocate CPU to another process.
• Non-preemption: A process holds the CPU until it terminates or blocks (voluntarily relinquishes control).
• Arrival Time (AT): Time when a process enters the ready queue.
• Burst Time (BT): CPU execution time required by the process.
• Completion Time (CT): Time when the process finishes execution.
• Turnaround Time (TAT): Total time from arrival to completion. TAT = CT - AT.
• Waiting Time (WT): Time spent waiting in the ready queue. WT = TAT - BT.
• Response Time (RT): Time from arrival to the first CPU allocation. RT = First Allocation - AT.

Scheduling Mechanics

How to choose Round Robin Quantum?

Choosing the time quantum clock size is a critical trade-off:

  • Too small: Excessive context switching overhead destroys efficiency.
  • Too large: Becomes identical to First-Come First-Served (FCFS), resulting in terrible response times for interactive applications.
  • Rule of Thumb: 80% of CPU bursts should be shorter than the time quantum.

Multilevel Feedback Queue (MLFQ)

One of the most complex scheduler types. It organizes the ready queue into multiple priority tiers. Processes can migrate dynamically: CPU-bound processes drop to lower priority queues, while I/O-bound processes migrate upwards. This maximizes interactive responsiveness without requiring process profiling.

Multithreading & Synchronization

Concurrency vs Parallelism, shared data race conditions, memory safety, and lock styles.

Concurrency Fundamentals

Concurrency

The execution of multiple tasks overlapping in time. On a single-core CPU, this is achieved by rapidly switching execution context (interleaving processes), creating the **illusion** of simultaneous progress.

Parallelism

The execution of multiple tasks at the exact same physical instant. This requires multi-core, multi-processor hardware where distinct threads execute on separate physical CPU cores simultaneously.

Race Condition

A scenario where multiple threads access and manipulate the same shared resource concurrently, and the final value depends on the exact ordering of execution. Consider a simple count increment:

Thread A (Read): count = 0
Thread B (Read): count = 0
Thread A (Add):  count + 1 = 1
Thread B (Add):  count + 1 = 1
Thread A (Write): count becomes 1
Thread B (Write): count becomes 1 (Lost update! Output should be 2)

Critical Section Requirements

The code segment containing shared memory modifications. A valid solution must satisfy:

  • Mutual Exclusion: Only one thread can execute in the critical section at any instant.
  • Progress: If no thread is in the critical section, only threads waiting to enter can decide which one gets to enter. The decision cannot be delayed indefinitely.
  • Bounded Waiting: There is a limit on the number of times other threads can enter their critical sections before a waiting thread's request is granted (no starvation).
Locks, Semaphores & Atomicity

Mutex

Mutual Exclusion Lock. A locking primitive with an owner. Only the thread that locks the mutex can release/unlock it. Good for simple critical section protection.

Semaphore

A signaling primitive containing an integer counter. Non-owner based: any thread can call `signal()` to increment the semaphore, waking up waiting threads.

Binary Semaphore vs. Mutex

While a Binary Semaphore is restricted to values 0 and 1, it differs fundamentally from a Mutex:

  • Ownership: Mutexes have ownership. The thread that locks a mutex *must* unlock it. Semaphores can be signaled (unlocked) by any thread.
  • Use Case: Mutexes are for protecting data structures. Semaphores are for scheduling/producer-consumer signaling.
  • Reentrancy: Mutexes can support recursive locking (a thread can lock it multiple times). Semaphores deadlock if locked again by the same thread.

Spin Lock

A lock where a waiting thread continuously polls the lock status in a tight loop. Wastes CPU cycles (busy waiting), but avoided context switch cost. Used in kernel code where lock hold times are guaranteed to be extremely brief.

Read-Write Lock

Allows multiple threads to read shared data simultaneously (shared lock), but only one thread to write at a time (exclusive lock). Boosts read-heavy application throughput.

Advanced Memory Synchronization

Atomicity

An operation is atomic if it completes as a single, indivisible step relative to all other threads. Hardware primitives like **Compare-And-Swap (CAS)** provide atomicity.

Memory Visibility

CPU cores cache values in L1/L2 caches. Writes by Core A are not instantly seen by Core B unless variables are declared `volatile` or memory barrier synchronization instructions are run.

False Sharing

Occurs when two threads running on different CPU cores modify independent variables that happen to share the same cache line. Cores repeatedly invalidate each other's cache lines, destroying speed.

Thread-Safety & Reentrant Code

Thread Safety: A design guarantee that code functions correctly when called by multiple concurrent threads without side effects.

Reentrancy: A stronger condition: code is reentrant if it can be interrupted in the middle of execution, called again (re-entered) by another thread, and both calls complete safely. Reentrant code completely avoids global/static variables and only modifies stack/arguments.

Deadlocks & Classic Problems

Necessary conditions, avoidance safety checks, Banker's algorithm logic, and synchronization problems.

Deadlock Mechanics

What is a deadlock? Draw a Resource Allocation Graph.

A Deadlock is a system state where a set of processes are permanently blocked because each process holds a resource and waits for another resource held by another process in the set.

The 4 Necessary Coffman Conditions

All four must hold simultaneously for a deadlock to exist:

  1. Mutual Exclusion: At least one resource must be held in a non-shareable mode (only one process can use it at a time).
  2. Hold and Wait: A process must be holding at least one resource and requesting new ones that are currently held by other processes.
  3. No Preemption: Resources cannot be forcibly seized; they are released only voluntarily by the holding process.
  4. Circular Wait: Process P0 waits for resource held by P1, which waits for P2, ..., which waits for P0.

Deadlock Prevention

Eliminate at least one Coffman condition. The most practical is preventing **Circular Wait** by imposing a global ordering on all resources. A process can only request resource $R_i$ if it holds no resources numbered $> i$.

Deadlock Avoidance

The OS dynamically evaluates resource requests using the **Banker's Algorithm**. If granting a request leads to an **Unsafe State** (which could potentially lead to deadlock), the request is deferred.

How do databases avoid and detect deadlocks?

  • Detection (Wait-For Graph): The database runs a background thread that periodically inspects active transactions. It draws a wait-for graph (nodes are transactions) and checks for cycles. If a cycle is detected, it aborts one transaction (rollback) to release its locks.
  • Avoidance (Timestamps):
    • Wait-Die: Older transaction is allowed to wait. Younger transaction dies (abort and restart).
    • Wound-Wait: Older transaction immediately preempts ("wounds") the younger transaction. Younger transaction waits if older requests it.
Starvation, Deadlock, & Livelock
Concept Process State CPU Usage System Progress
Deadlock Blocked/Waiting 0% Permanently Halted
Livelock Active / Running 100% (Busy-waiting loop) Permanently Halted
Starvation Ready / Waiting 0% for starved task System makes progress for other tasks

Examples illustrating the difference:

  • Deadlock: Two cars meet head-on on a single-lane bridge. Neither can move forward, neither will back up. They sit forever.
  • Livelock: Two polite people meet in a hallway. They both step to their left to let the other pass, then both step to their right, constantly moving back and forth in perfect synchronization but making no forward progress.
  • Starvation: A small customer waits at a busy shop. Large, wealthy customers keep arriving, and the shopkeeper repeatedly serves them first. The small customer is ignored indefinitely but the shop operates fine.
Classic Synchronization Problems

Producer-Consumer

A shared bounded queue exists. The producer places items in it, and the consumer removes them. Primitives needed:
• `mutex` (protect queue integrity).
• `empty` counting semaphore (track empty slots, init to N).
• `full` counting semaphore (track filled slots, init to 0).

Readers-Writers

A database needs to support concurrent readers but exclusive writers. Primitives needed:
• `writeLock` mutex (protect database access).
• `mutex` (protect the reader count variable).
• `readCount` integer tracking active reader threads.

Dining Philosophers

5 philosophers sit around a table, each needing two chopsticks to eat. If everyone picks up their left chopstick first, a circular wait deadlock occurs. Resolved by resource ordering: the 5th philosopher picks up the right chopstick first.

Sleeping Barber

A barber sleeps if no customers are in the shop. Customers enter: if chairs are available, they sit and wait; if not, they leave. Coordinate barber sleep-wake cycles with customers using semaphores and bounded wait variables.

Concurrency Coding

Production-grade thread-safe data structures and coordination implementations.

1. Print Odd and Even (Two Threads)

Classic interview question coordinating alternating execution using condition variables:

#include <iostream>
#include <thread>
#include <mutex>
#include <condition_variable>

std::mutex mtx;
std::condition_variable cv;
int count = 1;
const int MAX_COUNT = 10;

void printOdd() {
    while (count < MAX_COUNT) {
        std::unique_lock<std::mutex> lock(mtx);
        cv.wait(lock, []() { return count % 2 != 0; });
        std::cout << "Odd Thread: " << count << std::endl;
        count++;
        cv.notify_all();
    }
}

void printEven() {
    while (count <= MAX_COUNT) {
        std::unique_lock<std::mutex> lock(mtx);
        cv.wait(lock, []() { return count % 2 == 0; });
        std::cout << "Even Thread: " << count << std::endl;
        count++;
        cv.notify_all();
    }
}
2. Bounded Blocking Queue

Thread-safe blocking queue using a circular array, a mutex, and two condition variables:

#include <vector>
#include <mutex>
#include <condition_variable>

class BoundedBlockingQueue {
private:
    std::vector<int> queue;
    int capacity;
    int head = 0;
    int tail = 0;
    int size = 0;
    std::mutex mtx;
    std::condition_variable not_full;
    std::condition_variable not_empty;

public:
    BoundedBlockingQueue(int cap) : capacity(cap), queue(cap) {}

    void enqueue(int element) {
        std::unique_lock<std::mutex> lock(mtx);
        not_full.wait(lock, [this]() { return size < capacity; });
        
        queue[tail] = element;
        tail = (tail + 1) % capacity;
        size++;
        
        not_empty.notify_one();
    }

    int dequeue() {
        std::unique_lock<std::mutex> lock(mtx);
        not_empty.wait(lock, [this]() { return size > 0; });
        
        int val = queue[head];
        head = (head + 1) % capacity;
        size--;
        
        not_full.notify_one();
        return val;
    }
};
3. Thread-Safe Counter (Atomic & CAS)

Implementing a lock-free thread-safe counter using standard hardware Compare-And-Swap (CAS):

#include <atomic>

class LockFreeCounter {
private:
    std::atomic<int> value{0};

public:
    void increment() {
        int current = value.load();
        // Optimistic spin loop using Compare-And-Swap (CAS)
        while (!value.compare_exchange_weak(current, current + 1)) {
            // If another thread updated value, CAS fails, 'current' is updated, retry.
        }
    }

    int getValue() const {
        return value.load();
    }
};
4. Read-Write Lock Implementation

Implementing a custom Readers-Writer Lock with priority prevention using mutexes and condition variables:

#include <mutex>
#include <condition_variable>

class RWLock {
private:
    std::mutex mtx;
    std::condition_variable cv;
    int readers = 0;
    bool writer_active = false;
    int waiting_writers = 0; // Prevent reader starvation

public:
    void lockRead() {
        std::unique_lock<std::mutex> lock(mtx);
        cv.wait(lock, [this]() { return !writer_active && waiting_writers == 0; });
        readers++;
    }

    void unlockRead() {
        std::unique_lock<std::mutex> lock(mtx);
        readers--;
        if (readers == 0) {
            cv.notify_all();
        }
    }

    void lockWrite() {
        std::unique_lock<std::mutex> lock(mtx);
        waiting_writers++;
        cv.wait(lock, [this]() { return !writer_active && readers == 0; });
        waiting_writers--;
        writer_active = true;
    }

    void unlockWrite() {
        std::unique_lock<std::mutex> lock(mtx);
        writer_active = false;
        cv.notify_all();
    }
};

Memory & Virtual Memory

Contiguous allocation, paging address translation, TLB access calculations, and page replacement traces.

Amazon SDE-1 Masterclass
Question: Explain virtual memory like I'm five years old (ELI5).

"Imagine you have a giant toy chest (the Hard Drive) that holds hundreds of toys, but you only have a small play table (RAM) that can hold three toys at a time. The Operating System is like your parent. When you want to play with a toy, your parent grabs it from the toy chest and puts it on the table. If the table is full, your parent swaps out a toy you haven't played with in a long time back to the chest to make room. Virtual memory is the magic table that makes you feel like you can play with all your toys at once!"

Why Virtual Memory?

  • Protects Memory: Prevents Process A from reading or modifying Process B's memory.
  • Enables Oversubscription: Spawns applications that require more memory than physical RAM installed, using the disk backing store.
  • Simplifies Development: Every process sees a uniform, contiguous logical memory space starting at address `0`.
Partitioning & Fragmentations

Internal Fragmentation

Occurs when memory is allocated in **fixed-size partitions** (e.g. standard pages). If a process requests 3 KB, but the page block is 4 KB, the remaining 1 KB remains allocated but unused. It is wasted internally.

External Fragmentation

Occurs when memory is allocated in **dynamic-size partitions** (e.g. segmentation). Over time, memory is carved into tiny blocks. Total free space may equal 10 MB, but if it is fragmented into ten 1 MB chunks, a new process requesting 2 MB cannot start because no contiguous block is available.

Paging vs. Segmentation

• Paging: Divides logical memory into fixed-size blocks (Pages). Divides physical memory into identical frames. Eliminates external fragmentation entirely but causes minor internal fragmentation in the last page.

• Segmentation: Divides memory into variable-sized chunks based on program sections (code, stack, heap). Aligns with programmer view, but causes external fragmentation and requires compaction overhead.

Swapping

The system-wide action of moving a process's entire memory image out of RAM onto disk (swap space) when memory pressure is high, and restoring it later when physical RAM becomes free.

Thrashing

A catastrophic operating state where the OS spends more time constantly writing and reading memory pages to disk (handling page faults) than executing actual instructions. Occurs when processes lack frames to hold their active working sets.

TLB Access Math

TLB lookup math.

The Translation Lookaside Buffer (TLB) is a fast cache located inside the CPU's memory management unit. Let:
• $h$ = TLB hit ratio.
• $c$ = TLB lookup time.
• $m$ = Main memory access time.

EMAT (Effective Access Time) = h * (c + m) + (1 - h) * (c + 2 * m)

Note: On a TLB miss, we must access memory twice: once to read the page table entry to find the frame, and a second time to retrieve the actual data byte.

Numerical Example

Given hit ratio $h = 90\%$, TLB lookup time $c = 10\text{ ns}$, memory access time $m = 100\text{ ns}$.

EMAT = 0.90 * (10 + 100) + 0.10 * (10 + 200)
     = 0.90 * 110 + 0.10 * 210
     = 99 + 21
     = 120 ns

Module 8

Inter-Process Communication (IPC)

Mechanisms for exchanging data across isolated boundary barriers.

1. IPC Mechanisms

Pipe (Anonymous Pipe)

Unidirectional channel stored in memory. Supports communication only between processes sharing a parent-child relationship. Managed via standard input/output file descriptors.

Named Pipe (FIFO)

Bidirectional channel represented as a special block file on the filesystem directory tree. Allows unrelated processes to read and write data streams.

Shared Memory

Processes request the kernel to map the same physical RAM frame directly to both virtual address spaces. Processes read and write directly to the same bytes without invoking system calls.

Sockets

Standard network protocol abstraction. Allows bidirectional stream communication between processes on the same machine (Unix domain sockets) or across distinct network machines (TCP/UDP).

Message Queue

System-wide queue managed by the kernel. Allows processes to pass formatted messages asynchronously. Unlike pipes, messages do not require continuous streaming read loops.

Signals

Asynchronous kernel notifications sent to a process to alert it of events (e.g. `SIGINT` for keyboard interrupt, `SIGSEGV` for bad memory access, `SIGKILL` to instantly terminate).

2. Core Interview Questions

Which IPC mechanism is the fastest? Why?

Shared Memory is the fastest IPC mechanism by a wide margin.

Why:

  • For other IPC types (like Pipes, Sockets, or Message Queues), the sending process must copy data from its user buffer into the kernel's memory buffer (System Call 1). The receiving process must then copy data from kernel buffer to its own user buffer (System Call 2). This involves context switches and duplicate RAM copies.
  • With Shared Memory, once the memory layout is mapped to both processes' spaces, writing data is identical to writing to a local array. It is a direct RAM transfer with **zero data copying** and **zero system call intervention** required for the transfer. (Synchronization must be coordinated using locks).

Difference between Threads and IPC.

  • Threads: Share the same address space. Synchronization is quick and done via locks, but a bug in one thread can access and corrupt memory belonging to another, or crash the process.
  • IPC: Crosses process boundaries. Processes are isolated; Process A cannot read Process B's memory. Safe and crash-isolated, but data transfer requires higher overhead.

File Systems & Disk Scheduling

Inode blocks, linking styles, and track seeks distance calculations.

1. Inodes & Links

What is an Inode?

An Inode (Index Node) is a data structure on Unix filesystems containing metadata describing a file object (owner, size, file permissions, creation date, modification date) and an index array of block pointers pointing to where the file's raw bytes reside on disk.

Hard Link

A directory entry pointing directly to the Inode of the target file. Deleting the original name has no effect on the file data until all hard links are deleted. Cannot cross filesystem partitions.

Soft Link (Symbolic Link)

A separate file containing the path string to the original file. If the original file is deleted, the symbolic link breaks (becomes a dangling reference). Can span cross-partition boundaries.

Journaling

A filesystem design that writes metadata changes to a log file (journal) *before* committing them to the primary disk. If a crash or power failure occurs, the filesystem replays the journal on reboot, avoiding metadata corruption.

Buffer Cache

An area in main memory (RAM) used by the kernel to cache disk sector blocks. Reads and writes hit the cache first, avoiding physical disk seek latencies.

Modern Backend Concurrency

Mapping operating system concepts to distributed backend systems, web servers, and databases.

Web Server Mechanics

Why are thread pools used in web servers? What happens under load?

A thread pool bounds the maximum resources consumed by a server process. Thread creation is slow, so keeping warm thread pools ready avoids latency spikes.

What happens under load:

  • When simultaneous request traffic exceeds the thread pool size, incoming connection jobs are placed in an OS-level queue (backlog buffer).
  • If load continues to climb and the socket backlog buffer fills, the kernel drops or refuses connections, returning TCP resets or timed-out errors to clients.

Why doesn't every request get a new thread?

As discussed in Module 2: context-switching overhead, memory exhaustion (stack space limits), and CPU schedulers getting overloaded. Bounding threads via pools is necessary for stability.

Database Isolation & Scalability

How does a database handle concurrent transactions?

Databases guarantee transaction isolation (ACID properties) through synchronization primitives:

  • Locks: Pessimistic locking. Uses Shared Locks (S-locks) for readers, and Exclusive Locks (X-locks) for writers.
  • MVCC (Multi-Version Concurrency Control): Optimistic approach. Readers access a historical snapshot of the database while writers update a new version. Avoids blocking readers, maximizing database scalability.

Why are asynchronous event-loop servers (like Node.js) scalable?

Node.js runs single-threaded for JS code but delegates heavy operations to background system threads. It utilizes non-blocking system calls:

  • When Node performs an I/O request (e.g., querying database), it registers a callback and moves to handle other incoming events.
  • The kernel handles the I/O block. When completed, the OS notifies the event loop, which schedules the JS callback to run. This allows a single thread to multiplex thousands of active connections without thread overhead.

When should you use Multiprocessing instead of Multithreading?

  • Multiprocessing: CPU-bound tasks (e.g., video compression, heavy mathematical rendering, machine learning inference). Essential in languages like Python due to the **Global Interpreter Lock (GIL)** which prevents threads from running code on multiple CPU cores simultaneously.
  • Multithreading: I/O-bound tasks (e.g., network APIs request batching, real-time chats, filesystem logs). Beneficially shares memory structures and has very low instantiation cost.
