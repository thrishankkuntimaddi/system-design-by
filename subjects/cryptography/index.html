Security Architecture

High-Level System Overview

Production-grade End-to-End Encrypted (E2EE) messaging architectures, trust boundaries, and communication strategies.

E2EE Model Philosophy
An End-to-End Encrypted (E2EE) message system ensures that payloads are encrypted on the sender's device and can only be decrypted on the recipient's device. The intermediate server handles routing and message persistence in a zero-knowledge manner — the backend never sees plaintext messages or keys.
Core Architectural Pillars

Key Exchange Model

Diffie-Hellman Key Exchange (ECDH): Ephemeral or double-ratchet models are used to establish unique session keys between participants. Public keys are registered on the database, allowing offline negotiation.

Message Encryption

Authenticated Symmetric Encryption (AES-GCM): Message payloads are encrypted using a derived 256-bit symmetric session key with random 96-bit Initialization Vectors (IVs) and authentication tags to guarantee integrity.

Transport Channel

Real-Time WebSockets (Socket.IO): Delivers low-latency message relaying between connected clients. Authentication occurs during the socket handshake using cryptographically signed tokens (JWTs).

Storage Strategy

Encrypted persistence: The server stores the payload's ciphertext, iv, and auth_tag. Routing metadata (timestamps, sender/receiver IDs) is plaintext, but payloads are locked.

Trust Boundaries & Attack Surface
Client-Side Secure Boundary
  • Private keys are generated locally and never transmitted to the network.
  • Private keys are decrypted in memory only using a key derived from password hashing (PBKDF2/Argon2).
  • Compromise of the database or transport channel does not expose message contents.
Remaining Attack Surface
  • Metadata Leakage: Server knows who is communicating, when, and how frequently.
  • XSS / Local Exploits: If keys are stored in localStorage, a cross-site scripting attack can leak them.
  • MITM Key Substitution: A malicious server could return its own public keys instead of the receiver's.
E2E Flow

End-to-End Encryption Lifecycle

The cryptographic progression of a message from local generation, socket routing, database storage, and remote decryption.

Sequential Steps
1. User Registration & Key Generation:
During signup, the client browser generates a public/private asymmetric key pair (Curve25519 for key exchange).
  • Public Key: Sent to the server and persisted in the users database column.
  • Private Key: Encrypted locally using a key derived from the user's password using PBKDF2/scrypt, then stored in IndexedDB.
2. User Login & Key Retrieval:
The user authenticates with the server to retrieve their encrypted private key bundle. The local client uses the entered password to derive the key-encryption-key (KEK), decrypting the private key locally into volatile web memory.
3. Conversation Initialization:
When User A starts a chat with User B:
  1. User A requests User B's public key from the backend.
  2. User A performs an ECDH (Elliptic Curve Diffie-Hellman) operation with User B's public key and User A's private key to derive a shared_secret.
  3. The shared_secret is run through a HKDF (HMAC-based Key Derivation Function) to derive a 256-bit symmetric session key: aes_session_key.
4. Message Transmission (Encrypt & Send):
User A encrypts the plaintext payload using AES-256-GCM with the derived aes_session_key and a random IV. The socket client emits: 
socket.emit("send_message", {
  recipientId: "userB_uuid",
  ciphertext: "d7a8f9...",
  iv: "3e4b...",
  authTag: "fa2b..."
});
5. Message Persistence:
The socket server validates User A's authentication token (JWT), saves the encrypted packet (ciphertext, IV, authTag) in the SQL DB, and forwards the event to User B's active socket room.
6. Message Decryption:
User B receives the packet via their socket connection. User B computes the same session key using their private key and User A's public key, then decrypts the ciphertext using AES-256-GCM with the provided IV and validates the integrity tag.

Sockets

Socket Architecture Deep Dive

Real-time message routing, connection handshakes, namespaces, and delivery verification flow.

Connection Handshake & Auth
To prevent unauthorized messaging, the socket connection performs a cryptographically validated handshake. Clients must pass a valid JWT in the connection query parameters: 
const socket = io("https://chat.cnotes.io", {
  auth: { token: "JWT_TOKEN_HERE" }
});
The backend verifies the signature on the JWT. If invalid, the connection is immediately closed. Upon success, the socket associates the connection ID with the verified userId.
Room & Routing Configuration

Each user joins their own private notification room user_<userId> on connect. This design avoids shared room states and prevents information leakage.

1. Join Room

On connection, the backend calls socket.join("user_" + socket.userId). All incoming payloads for this user are emitted directly to this targeted room.

2. Delivery Acks

When User A sends a message to User B, User A registers a callback handler. When User B receives and decrypts the message, they emit a delivery receipt back to the server, resolving the callback.

Cryptographic Analysis

Deep dive into algorithm choices, key sizes, Initialization Vectors, and security rationale.

Cryptographic Choices
Primitive Type Algorithm Choice Rationale & Key Sizes Misuse Risks
Asymmetric Keys X25519 (ECDH) 256-bit key size. High security, extremely fast key derivation. Native to browser WebCrypto API. Reusing ephemeral keys indefinitely (mitigated by key rotation or Double Ratchet).
Symmetric Cipher AES-256-GCM 256-bit key. Galois Counter Mode provides **AEAD** (Authenticated Encryption with Associated Data). IV Reuse: Reusing the same IV with the same key destroys confidentiality and integrity guarantees.
Key Derivation HKDF (SHA-256) Extracts and expands entropy from ECDH shared secrets to produce cryptographically strong symmetric keys. Using raw DH shared secrets as symmetric keys directly without expansion.
Password KEK Argon2id / PBKDF2 Memory-hard hashing function to encrypt local key bundles on disk. Using weak iterations or lack of unique salting leading to dictionary lookup attacks.
Critical Alert: The IV Rules
IMPORTANT: For AES-GCM, the Initialization Vector (IV) MUST be exactly 96-bits (12 bytes) and MUST be cryptographically random for every single message encrypted under the same session key. Never hardcode an IV or increment it predictably.
Threat Model

Threat Model Evaluation

Evaluating the architecture against standard cybersecurity attack vectors and exploits.

Attack Vector Analysis

Man-in-the-Middle (MITM)

Threat: The server acts as a proxy, returning a fake public key to User A so it can decrypt messages.

Mitigation: Visual safety numbers (computed from hashes of public keys) are compared out-of-band by users, or public keys are signed by a Certificate Authority.

Compromised Server Database

Threat: An attacker steals all records from the messages table.

Mitigation: Payloads are stored as ciphertext. Only metadata (sender ID, time) is exposed. Message content remains secure.

Replay Attacks

Threat: An attacker intercepts an encrypted message packet and forwards it to the recipient repeatedly.

Mitigation: The encrypted packet contains a sequence counter and timestamp. Recipient rejects duplicated or expired sequences.

XSS Key Leakage

Threat: A cross-site scripting script accesses local IndexedDB variables and exfiltrates private keys.

Mitigation: Keys are kept in-memory (volatile storage) or loaded only within a sandbox Web Worker that restricts DOM access.

Forward Secrecy Definition
Forward Secrecy: If an attacker compromises the private keys of User A or User B today, they must not be able to decrypt past conversations. This is achieved by generating **ephemeral keys** that are destroyed after a session is closed.
Journey

End-to-End Message Journey

Following a single text string "Hello" from User A's terminal keystrokes to User B's screen render.

Step-by-Step Execution Path
  1. Client A Keystroke: User A types "Hello" and presses send. The front-end triggers sendMessage("Hello", "recipient_uuid").
  2. Symmetric Key Lookup: The front-end fetches the 256-bit symmetric session key for the target from local memory.
  3. Encryption: The crypto handler generates 12 random bytes (IV) and encrypts the string "Hello" into a base64 ciphertext (e.g. +x09jF/3...) and extracts a 16-byte auth tag.
  4. Socket Emission: The client emits the packet over a TLS-encrypted WebSocket channel to the node backend.
  5. Backend Interception: The message controller extracts the packet, logs routing metadata, and executes an INSERT query to database to save the ciphertext.
  6. Relay routing: The socket server routes the payload to User B's active socket channel: socket.to("user_recipient_uuid").emit("receive_message", packet).
  7. Decryption: User B's browser triggers the event, retrieves the session key, and executes the WebCrypto GCM decryption. The output string "Hello" is rendered on the viewport.
Audit Results

Architectural Weaknesses & Refactors

Security improvements, architectural adjustments, and optimization strategies for secure communication engines.

Identified Vulnerabilities & Recommendations

Weakness 1: Static Public Keys

If user keys remain static indefinitely, a compromise of the private key allows decryption of all historical messages.

Refactor: Implement a **Double Ratchet** protocol (e.g. Signal Protocol) where keys are rotated dynamically for every message exchanged.

Weakness 2: Plaintext Metadata

The backend stores database logs containing clear associations of sender ID, receiver ID, and timestamps.

Refactor: Use **Sealed Sender** headers (encrypting the sender identity using the recipient's public key) so the backend only routes to the recipient without knowing the sender.

Weakness 3: Memory Exhaustion

Relaying large binary payloads or media content through WebSockets places load on socket server thread memory.

Refactor: Clients upload large files to an S3 bucket encrypted with a one-time symmetric key, passing only the download link and key over the socket.

Weakness 4: Key Retrieval MITM

A compromised backend database could substitute the public keys returned to clients during session initialization.

Refactor: Use **Key Transparency** logs (similar to Certificate Transparency) where key modifications are appended to a tamper-proof public ledger.

Chapter 01

Fundamentals of Cryptography

Deep dive into cryptographic vocabulary, mathematical models of encryptions, and basic shift operations.

1. Core Vocabulary & Concepts
• Plaintext (P): The original, readable message string or byte buffer before being processed by a cipher. E.g., "HELLO".
• Ciphertext (C): The scrambled, unreadable output of an encryption algorithm. To unauthorized parties, it should appear as cryptographically random noise.
• Encryption (E): The mathematical operation mapping plaintext and a key to ciphertext: E(P, K) = C.
• Decryption (D): The process of reconstructing plaintext from ciphertext using a key: D(C, K) = P. For a correct cipher, D(E(P, K), K) == P holds true.
• Cipher: The mechanical, electrical, or mathematical algorithm containing the logical steps for encryption and decryption.
• Cryptographic Key (K): A variable parameter (usually a string of random bits) that alters the cipher output. Its secrecy is the sole guarantor of confidentiality (Kerckhoffs's Principle).
• Cryptanalysis: The science of hacking or reverse engineering, cracking, or decyphering ciphertext without authorization or prior possession of the correct keys.
• Cryptology: The overarching discipline combining both cryptography (designing ciphers) and cryptanalysis (breaking ciphers).
2. Mathematical Models & Kerckhoffs's Principle

Modern systems assume the algorithm is public. The security of the system rests entirely on keeping the key secret.

Kerckhoffs's Principle (1883): A cryptographic system should be secure even if everything about the system, except the key, is public knowledge. This is the foundation of open security standards (AES, RSA, TLS) where public review ensures no backdoors exist.
Symmetric Cipher Equation: C = E_K(P) <=> P = D_K(C)

If the key is chosen from a key space of size 2N (where N is the key length in bits), an attacker performing a brute-force search must search through 2N combinations. A key size of 128 bits yields a key space of 3.4 x 1038 combinations, making brute force physically impossible with current computing boundaries.

3. Detailed Step-by-Step Example: Caesar Cipher

The simplest substitution cipher: shifting letters along the modulo circle.

We map the English alphabet to numbers modulo 26: A = 0, B = 1, C = 2, ..., Z = 25. The encryption shift formula is:
C_i = (P_i + K) mod 26
The decryption shift formula is:
P_i = (C_i - K) mod 26
Trace of Plaintext "HELLO" with Key K = 3:
• H -> Index 7. Encrypt: (7 + 3) mod 26 = 10 -> K
• E -> Index 4. Encrypt: (4 + 3) mod 26 = 7 -> H
• L -> Index 11. Encrypt: (11 + 3) mod 26 = 14 -> O
• L -> Index 11. Encrypt: (11 + 3) mod 26 = 14 -> O
• O -> Index 14. Encrypt: (14 + 3) mod 26 = 17 -> R
Plaintext: HELLO
Ciphertext: KHOOR
Chapter 02

Goals of Cryptography

The core pillars of information security (CIA triad + Non-Repudiation) and their cryptographic enforcement.

1. Core Guarantees & Cryptographic Primitives
Goal Definition Threat Model Vector Cryptographic Primitive
Confidentiality Ensures unauthorized entities cannot read the payload data. Passive Eavesdropping, Man-in-the-Middle sniffing. Symmetric Encryption (AES-GCM, ChaCha20), Asymmetric Encryption (RSA, ECIES).
Integrity Guarantees data has not been modified, deleted, or added to in transit. Active Tampering, bit-flipping attacks, data corruption. Cryptographic Hash Functions (SHA-256, SHA-3), Message Authentication Codes (HMAC).
Authentication Verifies the true identity of the communication peer. Identity spoofing, impersonation, phishing. Digital Certificates (X.509), Digital Signatures (ECDSA), challenge-response handshakes.
Non-Repudiation Prevents the sender from denying they generated or sent a payload. Fraudulent denial of transactions, message forging. Asymmetric Digital Signatures (only the owner of the private key could sign the message).
2. Breach Scenarios & Real-World Impacts
How Goals are Met in HTTPS
  • Confidentiality: Payload encrypted using AES-GCM symmetric session keys.
  • Integrity: Handshake messages checked with SHA-256 MAC tags.
  • Authentication: Server certificate verified against Root CAs.
Typical Security Failures
  • Confidentiality Breach: Storing passwords or API keys in plaintext inside databases.
  • Integrity Failure: Relaying database records without signature tags, allowing parameter manipulation.
  • Authentication Spoofing: Trusting client-declared headers (e.g. X-User-ID) without JWT verification.
Chapter 03

Classical Cryptography

Pencil-and-paper ciphers, monoalphabetic substitution, polyalphabetic Vigenère grids, and transposition patterns.

1. Substitution Ciphers & Frequency Analysis
• Monoalphabetic Substitution: Maps each letter of the alphabet to a unique counterpart in a scrambled alphabet. E.g., `A` always maps to `Q`, `B` always maps to `W`, etc.
• Vulnerability (Frequency Analysis): In any language, letters appear with predictable frequencies. In English, `E` (~12.7%), `T` (~9.1%), and `A` (~8.2%) are most common. By calculating character counts in large ciphertexts, attackers can rebuild the lookup mapping table instantly.
2. Polyalphabetic (Vigenère) & Grid Substitution

The Vigenère Cipher mitigates frequency analysis by using a keyword to shift letters. Each letter in the key determines the Caesar shift for the corresponding message letter. The key repeats to match the length of the plaintext.

Vigenère Formula: C_i = (P_i + K_(i mod len(K))) mod 26
Example Trace:
Plaintext: ATTACK | Key: KEY
Repeated Key: KEYKEY
• A (0) + K (10) mod 26 = 10 -> K
• T (19) + E (4) mod 26 = 23 -> X
• T (19) + Y (24) mod 26 = 43 mod 26 = 17 -> R
• A (0) + K (10) mod 26 = 10 -> K
• C (2) + E (4) mod 26 = 6 -> G
• K (10) + Y (24) mod 26 = 34 mod 26 = 8 -> I
Ciphertext: KXRKGI
3. Block and Transposition Ciphers (Playfair, Rail Fence, Hill)
Playfair Cipher: Encrypts pairs of letters (digrams) using a 5x5 key matrix.
  • If the two letters are in the same row, replace with the letter immediately to their right (wrapping around).
  • If in the same column, replace with the letter immediately below (wrapping around).
  • Otherwise, form a rectangle and pick the letters at the opposite corners in the same row.
Rail Fence (Transposition) Cipher: Scrambles the position of letters (transposition) by writing the message diagonally in a zig-zag across imaginary rails: 
Plaintext: "SECRET MESSAGE", Rails: 3
S . . . E . . . E . . . G .
. E . R . T . M . S . A . E
. . C . . . S . . . S . . .
Ciphertext read row-by-row: "SEEGERTMAECCS"
Hill Cipher: Combines letters into vectors and encrypts them using matrix multiplication.
Vector C = (Matrix K * Vector P) mod 26
For example, to encrypt `HE` (7, 4) with Key Matrix [[3, 3], [2, 5]]:
C_1 = (3*7 + 3*4) mod 26 = 33 mod 26 = 7 (H)
C_2 = (2*7 + 5*4) mod 26 = 34 mod 26 = 8 (I) => Ciphertext: "HI"
To decrypt, the matrix must be invertible modulo 26 (i.e. determinant must share no common factors with 26).
Chapter 04

Symmetric Key Cryptography

Stream vs Block ciphers, operational modes (ECB vs CBC vs GCM), and padding standards.

1. Stream Ciphers vs. Block Ciphers
Stream Ciphers (e.g. ChaCha20, RC4)
  • Encrypts plaintext 1 bit/byte at a time.
  • Generates a pseudo-random keystream XORed directly with plaintext.
  • Extremely fast, low latency, ideal for real-time video/audio streaming.
  • Critical Rule: NEVER reuse the same key and IV/nonce (destroys security instantly).
Block Ciphers (e.g. AES, DES, Blowfish)
  • Encrypts data in fixed-sized chunks called blocks (typically 64 or 128 bits).
  • Requires padding (PKCS#7) if plaintext is not an exact multiple of the block size.
  • Requires a Mode of Operation to secure multiple blocks of data.
  • Less vulnerable to key-reuse attacks than stream ciphers (though still highly vulnerable in CBC mode).
2. Cipher Modes of Operation
Mode Description Parallelization Security Level & Rationale
ECB (Electronic Codebook) Encrypts each block independently. Identical plaintext blocks yield identical ciphertext blocks. Yes (both Encrypt & Decrypt) UNSAFE: Leaks structural patterns (e.g., the ECB Penguin image leak). Never use in production.
CBC (Cipher Block Chaining) XORs each plaintext block with the preceding ciphertext block before encryption. Requires an IV. Decrypt only LEGACY: Vulnerable to **Padding Oracle Attacks** (Manger's/Lucky13) if error messages leak timing details.
CTR (Counter Mode) Turns a block cipher into a stream cipher by encrypting an incrementing counter value. Yes (both Encrypt & Decrypt) SECURE: High performance, but does not check data integrity.
GCM (Galois/Counter Mode) Combines CTR mode with a Galois MAC tag computation to provide **AEAD** (Authenticated Encryption). Yes (both Encrypt & Decrypt) RECOMMENDED: Guarantees confidentiality and data integrity. Modern standard for TLS/Web.
3. Padding Standards (PKCS#7)
PKCS#7 Padding: Adds bytes to the end of the plaintext so its total length matches a block boundary. The value of each added byte is equal to the number of padded bytes.

• If 3 bytes of padding are needed for a 16-byte block, the padded bytes are: 0x03 0x03 0x03.
• If the plaintext is already an exact multiple of the block size, a **full block of padding** is appended (e.g., 16 bytes of 0x10) to prevent decryption ambiguity.
4. AES Block Structure and Rounds
AES (Advanced Encryption Standard) is a Rijndael block cipher. It maps a 128-bit (16-byte) block into a 4x4 matrix of bytes called the **State**. Each round (10 for AES-128, 12 for AES-192, 14 for AES-256) applies four steps:
  1. SubBytes: Substitution S-box mapping bytes non-linearly to prevent mathematical algebraic exploits.
  2. ShiftRows: Circular shift transpositions of the State rows (row 0: 0 bytes, row 1: 1 byte, row 2: 2 bytes, row 3: 3 bytes).
  3. MixColumns: Matrix multiplication over Galois Fields (GF(28)) to diffuse changes across columns.
  4. AddRoundKey: Bitwise XOR of the State with the subkey derived from the master key.
Chapter 05

Asymmetric Cryptography

Public/private keypairs, prime integer arithmetic, RSA key generation proof, and Elliptic Curve security benefits.

1. Asymmetric Model Concept
Symmetric ciphers suffer from the **Key Distribution Problem**: how do two remote parties securely share a key without a secure channel? Asymmetric cryptography solves this by using mathematically linked keypairs:
  • Public Key: Shared openly with the world. Anyone can use it to encrypt messages or verify signatures.
  • Private Key: Kept secret by the owner. Only the owner can use it to decrypt messages or sign payloads.
2. Mathematical Principles & RSA Keygen Proof

RSA (Rivest-Shamir-Adleman) relies on the **Trapdoor One-Way Function** of prime factorization: multiplying two large primes is easy, but factoring the resulting modulus back into primes is computationally infeasible.

RSA Key Generation Algorithm:
1. Select two prime integers: p = 61 and q = 53.
2. Compute modulus:
n = p * q = 61 * 53 = 3233
3. Compute Euler Totient:
φ(n) = (p - 1)(q - 1) = 60 * 52 = 3120
4. Choose public exponent e such that gcd(e, φ(n)) == 1. Let e = 17.
5. Calculate private exponent d as the modular multiplicative inverse: d * e ≡ 1 mod φ(n). Using the Extended Euclidean Algorithm:
d = 17^-1 mod 3120 = 2753
6. Public Key is (e=17, n=3233). Private Key is (d=2753, n=3233).
RSA Encryption & Decryption Example:
Let message be M = 65.
• Encrypt:
C = M^e mod n = 65^17 mod 3233 = 2790
• Decrypt:
M = C^d mod n = 2790^2753 mod 3233 = 65
3. Elliptic Curve Cryptography (ECC)

Stronger security bounds using curve coordinates (y² = x³ + ax + b) with significantly smaller key sizes.

Security Strength (Bits) Symmetric Key Size (AES) Equivalent RSA Key size Equivalent ECC Key size
80 (Legacy) 80 bits 1024 bits 160 bits
112 (Deprecated) 112 bits 2048 bits 224 bits
128 (Secure) 128 bits 3072 bits 256 bits
256 (Highly Secure) 256 bits 15360 bits 512 bits

By shifting to 256-bit ECC, devices gain equivalent security to 3072-bit RSA while reducing processing overhead, transmission packet sizes, and memory usage. This is critical for mobile networks, smart cards, and IoT sensors.

Chapter 06

Hash Functions

One-way mathematical maps, preimage resistance properties, the Avalanche Effect, and the Birthday Paradox collision math.

1. Core Properties of Cryptographic Hashes
A cryptographic hash function takes an arbitrary-sized input message and map-digests it into a fixed-size bit string (e.g. 256 bits for SHA-256). It must satisfy:
  • Pre-image Resistance: One-way nature. Given hash h, it must be computationally impossible to reconstruct any input x such that H(x) == h.
  • Second Pre-image Resistance: Given a specific input x1, it must be impossible to find a different input x2 that hashes to the same value: H(x1) == H(x2).
  • Collision Resistance: It must be impossible to find *any* two arbitrary distinct inputs x and y such that H(x) == H(y).
2. The Avalanche Effect

The Avalanche Effect means a single bit change in the input completely alters the output digest, making the new hash appear uncorrelated with the original. This prevents attackers from guessing the input based on changes in the output.

Example using SHA-256:
• SHA-256("test") = 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
• SHA-256("test1") = 1b4f90f239384752c00223df1f82f2c8d239103e3f43cd3f21822cd15b0f00b21
3. Collision Math: The Birthday Paradox

Why finding collisions is much easier than finding the original input for a given hash.

The **Birthday Paradox** shows that in a room of just 23 random people, there is a 50.7% chance that at least two share the same birthday, even though there are 365 possible birthdays. Applying this to hash collisions:
For a hash function with an output size of n bits (giving 2n possible hashes), the number of random inputs needed to find a collision with a 50% probability is not 2n, but only:
Operations to Collision ≈ sqrt(2^n) = 2^(n/2)
Consequently:
• For MD5 (128-bit): Collisions can be found in just 264 iterations (practically broken).
• For SHA-256 (256-bit): Collisions require 2128 operations, which is still computationally infeasible today.
Chapter 07

Digital Signatures

Assuring authenticity, integrity, and non-repudiation using asymmetric key pairs.

1. Step-by-Step Signing and Verification Mechanics
Asymmetric ciphers are slow and cannot process large files directly. Digital signatures solve this by hashing the message first, then encrypting the hash with the sender's private key.
Signing Process (Sender A)
  1. Sender computes the hash of message M: h = H(M).
  2. Sender encrypts hash h with their private key: S = D(h, K_private_A).
  3. Sender transmits message M and Signature S together.
Verification Process (Receiver B)
  1. Receiver computes the hash of received message M: h' = H(M).
  2. Receiver decrypts signature S using Sender's public key: h = E(S, K_public_A).
  3. If h' == h, the signature is valid.
2. Mathematical Proof of RSA Signatures

Using the RSA key generation properties, where e and d are mathematically linked modular inverses:

Signing: S = H(M)^d mod n | Verification: H(M)' = S^e mod n

Proof: S^e mod n = (H(M)^d)^e mod n = H(M)^(d*e) mod n = H(M)^1 mod n = H(M)

Because only the owner has the private key d, only they can generate signature S. Anyone with the public key e can verify it, proving the message's origin (authentication) and that it has not been modified (integrity).

Chapter 08

Certificates & PKI

Managing trust, X.509 certificate formats, certificate chains, and revocation validation.

1. X.509 Certificate Fields
A digital certificate is a cryptographically signed document that binds a public key to an entity's identity (e.g. a domain name). Standardized under the **X.509** format, it contains:
  • Subject: The entity owning the public key (e.g., Common Name: cnotes.io).
  • Issuer: The Certificate Authority (CA) that validated the entity and signed the certificate.
  • Public Key: The entity's public key (RSA or ECC coordinates).
  • Signature Algorithm: The algorithm used to sign the certificate (e.g. sha256WithRSAEncryption).
  • Validity Period: The start and end dates for the certificate.
  • CA Signature: The cryptographic signature of the Issuer CA, generated using the CA's private key.
2. The Certificate Chain of Trust

How browsers trust certificates by tracing them back to built-in Root CAs.

+------------------------+
|   Root CA Certificate  | -> Built into browser/OS trust store. Self-signed.
+------------------------+
           | Signs
+------------------------+
| Intermediate CA Cert   | -> Signed by Root. Used to sign leaf certs to protect root.
+------------------------+
           | Signs
+------------------------+
|   Leaf Certificate     | -> Installed on the web server (e.g., cnotes.io).
+------------------------+
3. Certificate Revocation: CRL vs. OCSP
CRL (Certificate Revocation List)
  • The CA publishes a signed list of revoked certificate serial numbers.
  • Clients download the entire list periodically to verify certificate status.
  • Drawbacks: High bandwidth usage, latency, and lists can become stale.
OCSP (Online Certificate Status Protocol)
  • Clients query the CA's server directly to verify a certificate's status.
  • OCSP Stapling: The web server queries the CA's status periodically, signs the response, and sends ("staples") it to the client during the TLS handshake, reducing latency and protecting privacy.

Chapter 10

Message Authentication Codes

Symmetric checksum authentication, hash vulnerabilities, and the HMAC nested mathematical structure.

1. Why plain Hashes cannot Authenticate Messages
A cryptographic hash function (like SHA-256) guarantees **Integrity**, but not **Authenticity**. If a message is sent over an insecure network along with its hash, an attacker can modify the message, calculate a new hash for the modified message, and replace the original hash. The receiver will compute the new hash and accept the modified message as valid.

To prevent this, we use a **Message Authentication Code (MAC)**, which requires a **shared secret key** to compute the tag.
2. HMAC Mathematical Formula & Design

Constructing a MAC by simply prepending the key to the message (H(Key || Message)) is vulnerable to **Length Extension Attacks** in ciphers using the Merkle-Damgård construction (SHA-1, SHA-2). An attacker can append data to the message and compute a valid hash for the extended message without knowing the key.

To prevent length extension attacks, **HMAC** (Hash-based MAC) uses a nested structure with inner and outer padding:
HMAC(K, m) = H( (K ⊕ opad) || H( (K ⊕ ipad) || m ) )
• K: The shared secret key (padded to the block size of the hash function).
• opad: Outer padding (constant byte value 0x5C repeated).
• ipad: Inner padding (constant byte value 0x36 repeated).
• ⊕: Bitwise XOR operation.
• ||: Concatenation.
Chapter 11

Key Management

The key lifecycle: generation entropy rules, key storage security (HSMs), rotation strategies, and split secrets.

1. Key Lifecycle Phases

1. Generation & Entropy

Keys must be generated using high-entropy random number generators (CSPRNG) inside secure boundary hardware modules. Weak entropy allows attackers to predict generated keys.

2. Secure Storage

Private keys should never be stored in plain configurations or application source code. Always use dedicated Hardware Security Modules (HSMs) or cloud Key Management Services (KMS).

3. Rotation

Keys must be rotated periodically (e.g. every 90 days) to limit the amount of ciphertext encrypted under a single key, reducing the impact if a key is compromised.

4. Destruction

When a key is retired or revoked, it must be securely deleted from all systems and media to prevent decryption of historical archives (ensuring Forward Secrecy).

2. KMS & HSM Hardware Boundaries
• HSM (Hardware Security Module): A physical tamper-resistant device that generates, stores, and protects keys. Keys never leave the HSM in plaintext; all cryptographic operations (encryption, decryption, signing) are executed inside the module's secure memory boundary.
• KMS (Key Management Service): A cloud service (e.g. AWS KMS, GCP KMS) that manages key lifecycles and enforces access policies (IAM) for keys, while using HSMs on the backend.
3. Shamir's Secret Sharing (SSS)

To secure highly sensitive keys (like root keys), **Shamir's Secret Sharing** splits a secret into N unique shares. The secret can only be reconstructed if a threshold of T shares (where T ≤ N) are combined, preventing a single point of failure or compromise.

SSS relies on polynomial interpolation: any point on a 2D graph can reconstruct a polynomial of degree T-1 if T distinct coordinates are known.
Chapter 12

Diffie-Hellman Key Exchange

Negotiating shared secrets over public channels, mathematical validation proof, and MITM vulnerabilities.

1. Diffie-Hellman Exchange Walkthrough
Diffie-Hellman allows two remote parties (Alice and Bob) to establish a shared symmetric session key over insecure public channels without sending keys directly.
Step-by-step Math:
1. Alice and Bob agree on public parameters: a prime modulus p = 23 and generator g = 5.
2. Alice chooses private exponent a = 6, computes public value A:
A = g^a mod p = 5^6 mod 23 = 8
3. Bob chooses private exponent b = 15, computes public value B:
B = g^b mod p = 5^15 mod 23 = 19
4. Alice and Bob swap public values A and B.
5. Alice computes shared secret S:
S = B^a mod p = 19^6 mod 23 = 2
6. Bob computes shared secret S:
S = A^b mod p = 8^15 mod 23 = 2
Both arrive at the identical shared secret 2 without exposing their private exponents!
2. Mathematical Proof of Equality
Alice's calculation: S_Alice = B^a mod p = (g^b mod p)^a mod p = g^(b*a) mod p
Bob's calculation: S_Bob = A^b mod p = (g^a mod p)^b mod p = g^(a*b) mod p

Since multiplication is commutative (a * b = b * a), g^(a*b) ≡ g^(b*a) mod p.
3. Man-in-the-Middle (MITM) Vulnerability
Active MITM Vulnerability: Anonymous Diffie-Hellman does not authenticate the identities of the participants. An active attacker (Eve) can intercept A's public share and exchange a separate key with Alice, while simultaneously exchanging a key with Bob, decrypting and re-encrypting all traffic passing between them.

Mitigation: Authenticate key exchanges by signing the public key shares using digital signatures and certificates (e.g. ECDHE-RSA or ECDHE-ECDSA in TLS).
Chapter 13

Elliptic Curve Cryptography (ECC)

Coordinate geometry, point arithmetic equations, and curve standards (secp256k1 & Curve25519).

1. Elliptic Curve Coordinates & Point Arithmetic
Elliptic curve cryptography utilizes curves defined by the algebraic equation:
y² = x³ + ax + b
The coordinates of points on the curve form a group under a defined addition operation:
  • Point Addition (P + Q): Draw a line through points P and Q. The line will intersect the curve at a third point, R. Reflect R across the x-axis to find the sum point: P + Q = -R.
  • Point Doubling (2P): Draw a tangent line to the curve at point P. The line will intersect the curve at another point. Reflect this point across the x-axis to find 2P.
2. The Discrete Logarithm Problem on Curves (ECDLP)

Given a starting point P (generator) and a scalar multiplier k (private key), we compute the public key point Q = k * P by repeatedly doubling and adding.

The security of ECC relies on the difficulty of finding the scalar k given only points P and Q. This is the **Elliptic Curve Discrete Logarithm Problem (ECDLP)**, for which there are no known sub-exponential time solving algorithms.

3. Industry Standard Curves

secp256k1

A Koblitz curve defined by y² = x³ + 7 mod p. Used in Bitcoin, Ethereum, and other cryptocurrencies due to its efficient point addition properties.

Curve25519

A Montgomery curve optimized for fast ECDH key exchanges. Designed by Daniel J. Bernstein, it is highly resistant to timing attacks and is the standard curve for SSH, TLS 1.3, Signal, and WireGuard.

Chapter 14

Password Security

Protecting password databases: salts (preventing rainbow tables), peppers, and key stretching ciphers.

1. Why Simple Hashes Fail for Passwords
Hash functions like MD5 or SHA-256 are designed to be fast, which makes them insecure for password storage. An attacker with a stolen database can use GPUs to test millions of passwords per second.

Furthermore, without unique salting, users with identical passwords will have identical hashes, allowing attackers to crack multiple accounts simultaneously using **Rainbow Tables** (pre-computed lists of common passwords and their hashes).
2. Salt vs. Pepper
Cryptographic Salt
  • A unique, cryptographically random string generated for each user.
  • Appended to the password before hashing and stored in plaintext in the database alongside the hash.
  • Purpose: Ensures identical passwords yield different hashes, preventing rainbow table attacks.
Cryptographic Pepper
  • A secret key appended to all passwords before hashing.
  • Stored separately from the database (e.g. in environment variables or an HSM).
  • Purpose: Prevents attackers from cracking passwords even if they steal the database, as they still lack the pepper.
3. Key Stretching Algorithms

Using slow, memory-hard algorithms to resist brute-force attacks.

bcrypt

Based on the Blowfish cipher. Uses a configurable cost parameter to increase the number of hashing rounds, slowing down brute-force attempts.

scrypt

Designed to require a large amount of memory, making it highly resistant to parallel attacks using custom hardware (ASICs/GPUs).

Argon2id

The winner of the Password Hashing Competition (2015). Provides configurable memory, time, and parallelization parameters. Highly secure.

4. Code Implementation: Hashing with bcrypt

A standard implementation using Node.js to hash and verify passwords securely.

const bcrypt = require('bcrypt');

// Hash a password
async function hashPassword(password) {
  const saltRounds = 12; // Cost factor (2^12 rounds)
  const hash = await bcrypt.hash(password, saltRounds);
  return hash;
}

// Verify a password match
async function verifyPassword(password, storedHash) {
  const match = await bcrypt.compare(password, storedHash);
  return match;
}
Chapter 15

Cryptographic Attacks

Understanding attack classes: ciphertext-only, chosen-plaintext, timing, and padding oracle attacks.

1. Attack Classifications
Attack Class Attacker Capability Example Exploits
Ciphertext-Only (COA) Attacker only has access to encrypted ciphertexts. Frequency analysis, brute force key exhaustion.
Known-Plaintext (KPA) Attacker has access to pairs of plaintext and corresponding ciphertext. Linear cryptanalysis, historical decryption of static files.
Chosen-Plaintext (CPA) Attacker can obtain ciphertexts for any arbitrary plaintexts they choose. Differential cryptanalysis, block size determination.
Chosen-Ciphertext (CCA) Attacker can obtain decryptions of any arbitrary ciphertexts they choose. Manger's attack on RSA, Padding Oracle attacks.
2. Side-Channel and Timing Attacks
• Side-Channel Attack: Analyzes physical characteristics of the cryptographic implementation (e.g. power consumption, electromagnetic emissions) rather than the math itself.
• Timing Attack: Measures how long a cryptographic operation takes to complete. If string comparisons return early on mismatches (e.g., "apple" === "apricot" returns on index 2), an attacker can guess signature signatures byte-by-byte.

Mitigation: Always use **constant-time comparison** algorithms for secret keys and MAC tags.
3. Padding Oracle Attack

A padding oracle attack targets block ciphers in CBC mode. If the decryption server returns different error messages for invalid padding vs. invalid keys/signatures, an attacker can modify ciphertext bytes and send them to the server to decrypt messages byte-by-byte without knowing the key.

Chapter 16

Random Number Generation

Entropy, predictability, PRNGs, CSPRNGs, and Linux kernel entropy pools.

1. Types of Random Number Generators

PRNG

Pseudo-Random Number Generator. Uses mathematical formulas to generate sequences of numbers from a seed value. Fast but deterministic; if the seed is known, the entire sequence is predictable.

CSPRNG

Cryptographically Secure PRNG. Guaranteed to pass statistical randomness tests and be mathematically unpredictable. Essential for generating keys, salts, and session tokens.

TRNG

True Random Number Generator. Uses physical noise (e.g., thermal fluctuation, radio interference) as entropy. Slow but truly non-deterministic.

2. Operating System Entropy Pools

How Linux collects entropy and exposes random devices to userspace.

The Linux kernel gathers environmental noise (keyboard input, mouse movements, disk seek times) into an entropy pool.
  • /dev/random: Blocks execution if the entropy pool runs dry. Highly secure but slow.
  • /dev/urandom: Does not block; if entropy runs dry, it uses a CSPRNG to generate values. Recommended for almost all production security tasks.
3. Predictable Hashing Disasters (e.g., Dual_EC_DRBG)
In 2013, documents leaked by Edward Snowden confirmed that the NSA had inserted a backdoor into the Dual_EC_DRBG standard (an elliptic curve PRNG). By choosing specific public curve parameters, they could predict future random outputs, allowing them to decrypt TLS connections.

Developer Rule: Never use predictable PRNGs like Math.random() in Javascript for security tasks, as their internal states can be reconstructed from just a few outputs. Always use crypto.getRandomValues().
Chapter 17

Modern Applications

Real-world cryptographic implementations: Signal's Double Ratchet, PGP, WireGuard, and Zero-Knowledge Proofs.

1. Signal Protocol: Double Ratchet & X3DH
The Signal Protocol is the industry standard for E2EE messaging.
  • X3DH (Extended Triple Diffie-Hellman): Establishes a shared secret session key between two parties, even if one is offline, using pre-published public keys.
  • Double Ratchet: Updates session keys dynamically for every message exchanged using a combination of KDF chains and ephemeral ECDH exchanges. This guarantees **Forward Secrecy** and **Break-in Recovery** (compromising one key does not expose past or future messages).
2. PGP (Pretty Good Privacy)

PGP encrypts emails and files using a hybrid model:
1. Plaintext is encrypted with a fast, random symmetric key (e.g. AES).
2. The symmetric key is encrypted using the recipient's public key (RSA) and appended to the message.
3. Recipient uses their private key to decrypt the symmetric key, then decrypts the message payload.

3. WireGuard VPN

A modern VPN protocol that uses **Cryptographic Key Routing**. It binds tunnel IP addresses to peer public keys, using Curve25519 (ECDH), ChaCha20-Poly1305 (encryption), and BLAKE2s (hashing) to provide faster, simpler connections than IPsec or OpenVPN.

4. Zero-Knowledge Proofs (ZKP)

ZKP is a cryptographic method that allows one party (the prover) to prove to another party (the verifier) that they know a secret value without revealing any information about the secret itself (e.g., proving identity without revealing the password).
